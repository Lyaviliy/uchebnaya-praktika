## 2. Безопасность (SQL-инъекции)
Все динамические запросы параметризованы (`$1`, `$2` …), значения передаются отдельным массивом:
| Место | Запрос |
|---|---|
| **Текстовый поиск на главной** | `p.name ILIKE $2 OR pt.name ILIKE $2 OR p.inn LIKE $2 OR p.email ILIKE $2`; символы `%` и `_` из ввода дополнительно экранируются |
| Сохранение карточки | `INSERT ... VALUES ($1 … $8)`, `UPDATE ... SET ... WHERE id = $9` |
| Карточка, история, справочники | `WHERE id = $1` |
| Загрузка сырых файлов | `INSERT INTO staging... VALUES ($1 … $6)` |

`securityAudit.test.js` проверяет весь код и падает, если найдёт SQL со вставкой `${...}` или склейкой строк через `+`; на подложенном уязвимом запросе срабатывает.
Проверено вживую: ввод `' OR 1=1 --` в поиск находит 0 партнёров, `x'); DROP TABLE partners; --` в названии сохраняется как обычный текст.

## 3. Исключения и MessageBox
Все обращения к серверу и БД обёрнуты в `try...catch`, приложение не падает. Диалоги (`public/dialogs.js`):
- **Ошибка** (красный крестик): неверный ввод, недоступная БД, дубликат ИНН/email, расчёт вернул -1. Текст содержит **пронумерованный порядок исправления**
- **Предупреждение** (жёлтый знак): «Назад» при изменённых полях — о необратимой потере несохранённых данных, «Да» / «Нет»
- **Информация** (синий «i»): успешное сохранение или добавление

Ошибки пишутся в `logs/app.log` с датой и временем (`src/logger.js`), пример — `logs/app.log.example`.

## 4. Комментарии
Только в неочевидных местах: очистка погрешности перед округлением, смысл -1, передача id между окнами через адрес, экранирование `%` и `_` в поиске, разбор кавычки-дюйма, исправление латинских инициалов в ETL.
