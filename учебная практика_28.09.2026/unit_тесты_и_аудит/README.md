## 2. Аудит безопасности (защита от SQL-инъекций)
Проверены все SQL-запросы приложения (`src/partnerService.js`, `src/materialService.js`, `scripts/initDb.js`):

| Место | Как защищено |
|---|---|
| список, карточка, история продаж партнёра | `WHERE p.id = $1`, значение передаётся массивом параметров |
| добавление / изменение партнёра | `INSERT ... VALUES ($1 … $8)`, `UPDATE ... SET ... = $1 … WHERE id = $9` |
| справочники для расчёта | `WHERE id = $1` |
| создание базы | имя базы нельзя передать как `$1`, поэтому экранируется `escapeIdentifier`; к тому же оно берётся из конфига, а не от пользователя |
| id в адресе (`/api/partners/1 OR 1=1`) | маршрут принимает только цифры, иначе 404 |

Аудит автоматизирован: `test/securityAudit.test.js` проходит по всему коду и падает, если найдёт SQL со вставкой `${...}` или склейкой строк через `+`.
Проверено: подложенный уязвимый запрос тест находит.

Живая проверка: ввод в поле «Наименование» строки `x'); DROP TABLE partners; --` сохраняется как обычный текст, таблица цела.

## 3. Журнал ошибок
`src/logger.js` пишет в `logs/app.log` дату, время, уровень и текст ошибки (и дублирует в консоль):
- **ERROR** — непредвиденные исключения: недоступна БД, сбой сервера, непойманные ошибки
- **WARN** — ожидаемые ошибки: валидация, дубликат, не найден, расчёт вернул `-1`
- **INFO** — запуск сервера

Пример — `logs/app.log.example`. Сам `logs/app.log` в git не попадает (`.gitignore`).

node --test test/
